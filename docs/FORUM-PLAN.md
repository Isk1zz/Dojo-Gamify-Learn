# FORUM-PLAN.md — план реализации форума

*План написан 2026-09-01. Форум перестал быть заблокированным: шаги 0–7
бэкенда сделаны, аккаунты работают, RLS проверена пентестом, шаблон
`SECURITY DEFINER` RPC уже обкатан на `buy_course`.*

Это третий из трёх циклов приложения: **учить → удерживать → делиться**.
Первые два построены, этот — тот, ради которого они такой формы.

---

## Что уже решено (не пересматриваем без причины)

Эти решения приняты раньше и записаны в `UPDATESTACK.md` / `forum/FORUM.md`.
План опирается на них, а не изобретает заново.

| Пункт | Решение |
|---|---|
| Что тратим | **Репутацию**, не деньги и не токены |
| Накопление | **Нет.** Не баланс, а дневная норма |
| Хранение нормы | **Не хранится.** Сгорает ночью |
| На что тратим | Только на **чужие** посты. Никогда на свои |
| Потолок на человека | **10 очков одному автору в месяц** |
| Потолок на пост | **1 очко на пост** |
| Сезон | Календарный месяц |
| Достижения | Дают **статус, никогда валюту** |
| Где живёт репутация | `data/db.js`, поле профиля `wallet` (имя storage не меняем) |

**Почему нормой, а не балансом.** Накопление превращается в запас, запас
выигрывает стаж, а стаж превращает форум в клуб старожилов. Сгорающая
норма ещё и заставляет читать *сегодня*. Это проверенная схема — так
устроены mod points на Slashdot.

**Почему потолок 10/автор/месяц решает сговор.** Двое друзей, качающие
друг друга, перекачивают максимум 10 очков в месяц вместо ~150. Сговор
перестаёт быть стратегией, а не начинает патрулироваться. Из этого же
бесплатно следуют два свойства: чтобы потратить норму, нужно прочитать
**15–27 разных авторов**, и никого нельзя вытащить одним фанатом.

## Шаг 0 — три решения, которых не хватает. БЛОКИРУЮЩИЕ

Без них нельзя писать RPC: правила начисления живут на сервере, а сервер
должен знать точные числа.

### 0.1. Формула дневной нормы — ПЕРЕОТКРЫТА

Было `5 + floor(rank / 5)` (R1 = 5, R20 = 9). Переоткрыто 2026-08-27:
норма должна считаться **от пройденных блоков с учётом чанков внутри**,
с потолком.

Нужны конкретные числа. Например (это предложение, не решение):

```
норма = min(ПОТОЛОК, БАЗА + floor(завершённых_чанков / N))
```

Три вопроса, на которые нужен ответ:

1. **Чему равен блок?** Платит ли наполовину пройденный блок
   пропорционально чанкам или ничего?
2. **Каков потолок?** Это несущая конструкция, а не деталь. Причина, по
   которой старая формула держала разброс **меньше 2×**, — именно та
   проблема 44-кратного разброса, которая убила дивиденды Сада. Норма от
   учёбы растёт вместе с объёмом пройденного и воспроизведёт ту же
   проблему без потолка.
3. **По-прежнему сгорает?** Модель говорит «да». Формула от учёбы этому
   не противоречит, но подтвердить надо явно.

### 0.2. Что делает бан с постами

`admin/ADMIN.md`: бан — это **полная необратимая очистка аккаунта**.
Решение принималось для однопользовательского приложения.

На форуме это ломает чужой контекст: удаляется автор, на чьи посты
отвечали другие. Ветка превращается в набор ответов в пустоту.

Варианты: скрывать посты, но сохранять структуру («удалено»); удалять
всё; или разделить «бан» и «очистка» на два разных действия.

### 0.3. Модерация: кто и по какому сигналу

Жалобы нужны до, а не после запуска. Минимум: кнопка «пожаловаться»,
очередь для админа, флаг скрытия, применяемый на сервере.

## Шаг 1 — схема и RLS

Отдельной миграцией (`0007_forum.sql`). Правило прежнее: миграцию,
которая уже прогонялась на живом проекте, не редактируем — только новая.

```sql
create table public.posts (
  id          uuid primary key default gen_random_uuid(),
  author      uuid not null references auth.users(id) on delete cascade,
  body        text not null check (length(body) between 1 and 8000),
  created_at  timestamptz not null default now(),
  -- Модерация решается сервером. Клиент это поле не пишет.
  hidden      bool not null default false,
  -- Денормализованный счётчик: лента сортируется по нему, а считать
  -- COUNT(*) по grants на каждый рендер — это N+1 на пустом месте.
  -- Пишется ТОЛЬКО из RPC, никогда клиентом.
  score       int  not null default 0
);

create table public.replies (
  id          uuid primary key default gen_random_uuid(),
  post        uuid not null references public.posts(id) on delete cascade,
  author      uuid not null references auth.users(id) on delete cascade,
  body        text not null check (length(body) between 1 and 4000),
  created_at  timestamptz not null default now(),
  hidden      bool not null default false
);

-- Журнал начислений. ЭТО источник истины, а не posts.score.
-- Он же — то, чем принудительно соблюдаются оба потолка.
create table public.rep_grants (
  id          uuid primary key default gen_random_uuid(),
  giver       uuid not null references auth.users(id) on delete cascade,
  receiver    uuid not null references auth.users(id) on delete cascade,
  post        uuid not null references public.posts(id) on delete cascade,
  created_at  timestamptz not null default now(),
  -- 1 очко на пост: один даритель может начислить на конкретный пост
  -- ровно один раз. Это ограничение БД, а не проверка в коде.
  unique (giver, post),
  -- Никогда себе. Тоже ограничение БД: правило, которое нельзя обойти,
  -- даже если RPC когда-нибудь напишут неправильно.
  check (giver <> receiver)
);
```

**RLS — по образцу `economy`, а не `progress`:**

| Таблица | Чтение | Запись |
|---|---|---|
| `posts` | все авторизованные, кроме `hidden` | **нет политики** — только через RPC |
| `replies` | так же | **нет политики** — только через RPC |
| `rep_grants` | только свои строки (`giver = auth.uid()`) | **нет политики** — только через RPC |

Почему записи нет вообще: это ровно та схема, которая на пентесте
выдержала все атаки на `economy`. Если клиент может писать `score`
напрямую, все потолки — рекомендация. Отсутствие политики надёжнее любой
проверки, потому что нечего обходить.

**Готово выглядит так:** авторизованный клиент читает посты, но прямой
`insert`/`update` в любую из трёх таблиц возвращает 403 или меняет 0
строк — проверено так же, как на пентесте.

## Шаг 2 — RPC начисления. Главный шаг

Один `SECURITY DEFINER` на всю механику. Все правила — здесь, потому что
это единственное место, где их нельзя обойти.

```
grant_reputation(post_id uuid) → jsonb
```

Что проверяет, по порядку:

1. `auth.uid()` есть (иначе — 28000).
2. Пост существует и не скрыт.
3. **Автор поста ≠ вызывающий.** Не «на себя нельзя» в клиенте —
   ограничение БД плюс явная проверка.
4. **Не начислял на этот пост раньше** — `unique (giver, post)`.
5. **Не превысил 10 очков этому автору в текущем месяце** —
   `count(*) from rep_grants where giver = me and receiver = author
   and created_at >= date_trunc('month', now())`.
6. **Не превысил дневную норму** — норма считается на сервере по формуле
   из шага 0.1 (из `progress` того же пользователя), потраченное за
   сегодня — `count(*) ... where created_at >= current_date`.
7. Вставляет `rep_grants`, инкрементит `posts.score`.

**Норма нигде не хранится.** Она вычисляется: «сколько положено сегодня»
минус «сколько строк в журнале за сегодня». Из этого бесплатно следует,
что она сгорает ночью — не нужен ни cron, ни ночная задача, которых на
бесплатном тарифе всё равно нет. **Отсутствие поля и есть реализация
правила.**

**Готово выглядит так:** попытка начислить себе, начислить дважды на один
пост, начислить одиннадцатое очко одному автору за месяц и превысить
дневную норму — все четыре отказывают с разными кодами; честное
начисление проходит и увеличивает `score` ровно на 1. Проверяется тем же
способом, что и `buy_course`: обеими сторонами границы.

## Шаг 3 — три числа в профиле

Решено 2026-08-16: журнал **и есть** запись, отдельных счётчиков не
держим.

| Число | Сторона | Смысл |
|---|---|---|
| Отдано | дано | сколько всего роздано за всё время |
| Получено за месяц | получено | сезонная величина, обнуляется |
| Получено всего | получено | пожизненная, не обнуляется |

Все три — запросы к `rep_grants`, не поля. Сезон обнуляется сам, потому
что «за месяц» — это условие `where`, а не событие.

**Щедрость видна.** Показывать «отдано» рядом с «получено» — противовес
табло, которое иначе награждает только популярность. Дёшево сейчас и
невозможно добавить потом без данных, которых ни у кого не будет.

## Шаг 4 — лента и чтение

Обычный CRUD, сюрпризов нет. Сортировка по `score`, затем по дате.

Один момент, который стоит спроектировать сразу: **на маленьком форуме
норма почти не тратится.** Пять активных авторов — это максимум 50
размещаемых очков в месяц против нормы в ~150–270. Число будет выглядеть
сломанным, если интерфейс не скажет «до N в день» и не покажет, сколько
реально можно разместить. Дневную величину стоит пересмотреть, когда
станет известен объём постинга — поднять потом легко, срезать больно.

## Шаг 5 — публикация и ответы

RPC, а не прямой `insert`: сервер ставит `author = auth.uid()`, чтобы
нельзя было опубликовать от чужого имени. Плюс антиспам — минимальный
интервал между постами.

**Связь с Заметками.** Заметка — это черновик. «Опубликовать заметку» —
маленький шаг от того, что человек уже написал, и это способ получить
первый контент вместо чистого листа в первый день. Заметки всё равно
нужно синхронизировать (решено 2026-08-16, тот же батч).

## Шаг 7 — юридическое

С форумом приложение начинает **хранить пользовательский контент**, а не
только собственные данные пользователя. Это меняет `docs/LEGAL.md`:
нужен порядок обработки жалоб, правила о недопустимом контенте и
уточнение, что происходит с постами при удалении аккаунта (сейчас
`delete_account` каскадит — посты исчезнут, ветки порвутся; см. 0.2).

## Порядок

1. **Шаг 0** — три решения. Часы, без кода. Блокирует всё остальное.
2. **Шаг 1** — схема + RLS.
3. **Шаг 2** — RPC начисления. Тот шаг, ради которого всё остальное.
4. **Шаг 3–5** — профиль, лента, публикация.
5. **Шаг 6–7** — модерация и юридическое, до публичного запуска.

Первым кодом идёт не лента, а правила: лента без работающих потолков —
это форум, который придётся чинить с уже накопленными данными.
